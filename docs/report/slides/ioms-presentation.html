01 · Pembukaan

Masalah dan pengguna

Tim gudang dan sales perlu mencatat pembelian dari supplier dan penjualan ke customer di beberapa gudang, dengan angka stok yang bisa dipertanggungjawabkan, termasuk ketika dua proses berjalan bersamaan.

Status penyelesaian

Semua fitur wajib selesai: master data, PO, SO dengan approval, goods receipt/issue, perpindahan stok, stock ledger, laporan CSV, dashboard, dan endpoint JSON.

Kontribusi saya: perancangan dan implementasi proyek. Sebagian besar kode, test, dan dokumentasi dibuat dengan bantuan Claude Code, dan saya bertanggung jawab memahami dan menjelaskannya (lihat slide terakhir).

03 · Implementasi teknis

Integritas stok: tidak ada oversell

// SalesOrderService::fulfill()
$pdo->beginTransaction();
foreach ($items as $item) {
  $available = $stocks->lockForUpdate(...);
  // SELECT quantity ... FOR UPDATE
  if ($available < $item->qty) {
    throw InsufficientStockException;
  }
}
// decrement + tulis stock_ledger
$pdo->commit();   // kegagalan → rollBack()
  • Pessimistic row lock InnoDB: dua goods issue pada produk dan gudang yang sama dipaksa antre.
  • Cek stok dilakukan setelah lock, sehingga hasilnya tidak basi.
  • Kekurangan di satu item membatalkan seluruh transaksi: tidak ada stok setengah berkurang.
  • Terbukti lewat integration test terhadap MySQL asli dan test E2E.
  • Keputusan dan alternatif: ADR-002.
IOMS · Final Project05
03 · Implementasi teknis

Keamanan, frontend, dan Docker

Keamanan

  • password_hash / password_verify
  • session_regenerate_id saat login
  • Role dicek di server (Auth::requireRole)
  • Output di-escape; prepared statement
  • Upload: tipe MIME asli, maks 2MB, nama acak

Frontend dan JSON

  • HTML semantik, CSS sendiri, responsif
  • Vanilla JS: validasi form, baris item dinamis
  • Fetch API: GET /api/products/{sku}/availability
  • 401 tanpa login, 404 SKU tidak ada

Docker

  • docker compose up --build: app + MySQL
  • Schema dan seed diimpor otomatis
  • App berjalan sebagai non-root, ada healthcheck
  • Diverifikasi dari clone bersih

IOMS · Final Project08
05 · Refleksi

Kendala, keterbatasan, dan langkah berikutnya

Kendala dan solusi

  • Stok benar saat konkuren → transaksi + row lock.
  • Clone bersih gagal jalan (bind mount menimpa vendor/) → ketahuan saat verifikasi, diperbaiki.
  • Coverage Controller/view awalnya 0% → test E2E lewat HTTP.

Keterbatasan (jujur)

  • Tanpa rate limiting dan CSRF token.
  • API memakai session cookie; ApiController melewati Service.
  • 100% adalah line coverage, bukan semua kombinasi input.
  • Tanpa CI/CD.

Prioritas berikutnya

1ProductAvailabilityService 2Rate limiting login/API 3Audit log master data 4Token API & CSRF
